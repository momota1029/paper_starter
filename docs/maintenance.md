# 保守

この作業は論文生産のパイプラインを起動しない。利用者の改善要求に対応する
正本の規則、スキルの入口、担当のプロンプト、検査のどこが変わるかを先に特定する。
既存の個別原稿をルール変更だけのために改稿しない。

規則の変更は、適用範囲、問題となる具体例、問題のない近接例、確認方法を伴わせる。
単発の好みを全分野の禁止事項にしない。普通の会話で与えられた継続的な
文章作法の指示は改善要求として受け取り、重ねて「覚えるか」を確認しない。
意味のある反復や必要な留保まで機械的に削らない。

基本の確認:

```bash
python3 tools/paper.py check
python3 -m unittest discover -s tools/tests -v
git diff --check
```

新しい規則は [規則索引](../rules/INDEX.md) と必要なスキル・役割からリンクする。
[モデル指定](agents.md)を変更したら、TOMLの文法だけでなく実際の起動設定も確認し、
要求したモデルと実際に観測できたモデルを分けて報告する。
ライフサイクルフック、外部サービス、個人の認証情報を同梱しない。

文章品質に影響する変更では [評価手順](../evals/README.md) に従って、
欠陥の検出、適切な修正、良い文章を壊さないこと、読者の実際の理解を分けて測る。
修正を作った担当は自分の出力の独立評価をしない。
テストの正解や過去の指摘を初読者へ渡さない。
学習・開発用の例に合わせた改善は、別の未使用の例と実原稿で再確認する。

公開前には追跡対象を実際に調べる。ローカル原稿、著者情報、私信、第三者文献、
個人パス、APIキー、既存環境の設定を混入させない。Git除外だけを根拠にせず、
公開されるファイルの実物を点検する。
