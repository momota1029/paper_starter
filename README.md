# Paper Starter

資料の受け入れ、根拠の検証、論文の執筆、独立したレビューと修正を一つの
作業フォルダで進めるためのスターター。理論、実証、質的・人文学、レビュー論文に対応する。
原稿の構成を一律に固定せず、分野の実例と想定読者から決める。

原型の執筆環境から、skills → rules の参照、基本的な論理の点検、
設計・執筆・独立監査の分離、初読の観測、修正後の再確認を移植した。
個別の研究資料や特定の研究室の表記習慣は同梱していない。

## 使い始める

Python 3.11 以上で、追加パッケージなしに管理・検査コマンドを使える。
このフォルダを作業先として開き、まず次を実行する。

```bash
python3 tools/paper.py check
python3 -m unittest discover -s tools/tests -v
python3 tools/paper.py new my-paper --title '研究の題名' --profile empirical
```

`inbox/` に資料を置き、例えば次のように依頼する。

> inbox の資料から my-paper の論文を作りたい。読者は関連分野の研究者。
> 根拠が足りない主張を分け、構成を設計し、独立レビューと修正まで進めて。

> 導入を読んで何が問題なのか分からない。初読者がどこでつまずくかを調べ、
> 必要なら段落や節の順序まで直して、新しい読者で確かめて。

> この原稿を査読して。原稿は変更せず、位置・根拠・重要度・修正の条件を報告して。

[AGENTS.md](AGENTS.md) が [paper-writing](.agents/skills/paper-writing/SKILL.md)
へ案内し、スキルが必要な [rules](rules/INDEX.md) を読む。
対応するAI環境では自然な依頼から開始できる。他の環境では `AGENTS.md` を
入口として明示する。フォルダを置くだけで全てのAIが同じ機能を持つわけではない。

## フォルダ

```text
AGENTS.md                  AIの入口と共通の制約
.agents/skills/            執筆ワークフロー
.codex/agents/             Luna / Sol の実際のサブエージェント定義
.codex/config.toml         サブエージェントの同時実行数
rules/                    基本論理、文章作法、分野別検証、修正ループ
inbox/                    未整理・未検証の資料
writing/<slug>/            原稿の正本、根拠、設計、主張の記録
output/<slug>/             PDF / HTML、生成記録
refs/                     ローカルな参考文献
index.md                  全体の入口
writing/index.md          ローカル研究一覧（自動生成）
templates/                新規研究・報告書のひな型
tools/                    管理、凍結、検査と回帰テスト
evals/                    文章と運用の評価用素材
docs/                     設定、品質の範囲、保守
```

原稿・inbox・文献・出力・研究一覧は初期状態でGit対象外。
公開するスターターに自分の研究資料を混ぜずに使える。
共同研究の履歴をGitで管理する場合は、研究用リポジトリで追跡対象を明示する。

## サブエージェントと反復

[同梱の設定](docs/agents.md)では、Luna が資料の索引・限定した書誌照合・
初読の観測等を担当し、Sol が設計、執筆、論証、内容の正確性と引用の支持を担当する。
難しい判断をLunaの合否だけで確定せず、根拠を付けてSolへ渡す。
親のモデルは固定しない。利用できるモデルや実際に読み込まれた設定は実行環境で確認する。

基本の反復は、設計 → 執筆 → 独立レビュー → 指摘の照合 → 一括修正 → 新しい確認。
初読者には答えや修正意図を渡さず、読み進めた時点の理解を記録する。
直しても理解が回復しなければ設計へ戻る。変更のない再実行で合格を引く方式にはしない。
誤字修正は軽く、新規主張や投稿直前は広く確認する。

[品質契約](rules/quality-contract.md)に、読者の既有知識、外部入力の説明、
帰属を示す位置、近接論文への拘束力と著者が認めた例外を記す。
指摘なしの査読にも確認一覧を求め、分野ごとの厳しい条件を移行時に弱めない。
テキストの初読には、実行前の診断と元の観測を残す
[順次読者CLI](docs/reader-runner.md)も利用できる。

## 出力と検証

Markdown のHTML出力には Pandoc、TeXのPDF出力には LuaLaTeX と latexmk が必要。
編集・索引・レビュー記録の機能はこれらなしでも使える。

```bash
python3 tools/paper.py build my-paper
python3 tools/paper.py index --check
```

TeXで始める場合は `new ... --format tex --language en` とする。
同梱TeXは英語用の最小ひな型。日本語の組版や投稿先固有のクラスは実際の
環境とテンプレートに合わせて設定する。
ビルド後の目視確認、提出物だけでの再ビルド、著者の最終通読も必要。

レビュー対象の凍結、実際の報告の記録、版の一致の検査は
[コマンド説明](tools/README.md)を参照する。
`readiness` は確認記録の不足や古さを検出する補助であり、論文の正しさを認証しない。

[品質の対応と検証状況](docs/quality.md)には、機械検査、実際のAI評価、
人間による確認を区別して記載する。全分野の完成論文が自動的に一定品質に
なるという保証ではなく、必要な確認を飛ばさない仕組みとして使う。
