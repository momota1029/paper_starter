# Paper Starter

Paper Starter は、研究資料と論文原稿を一つの作業フォルダで管理するためのひな型・規則・コマンドをまとめたものだ。
資料を整理し、主張が出典に支えられているかを確かめながら、原稿の作成・改稿とレビューの記録を進める。
理論研究、実証研究、質的研究、人文学、レビュー論文などを想定するが、章立てや証拠の基準は分野、投稿先、読者に合わせて利用者が決める。

ChatGPT Pro で生成した資料や下書きを `inbox/` に持ち込み、内容と出典を確認しながら整理・整形する使い方を想定している。
生成した資料を出発点に、論文原稿や理解用ノートとして読める形に仕上げていく。

このスターターは研究資料や参考文献を提供せず、原稿の正しさや掲載可能性を自動判定するものでもない。
利用者固有の研究資料や、特定の研究室の表記習慣も含まない。

## 使い始める

管理・検査コマンドには Python 3.11 以上が必要で、追加パッケージは不要だ。
このフォルダを作業先として開き、状態を確認してから研究用フォルダを作る。

```bash
python3 tools/paper.py check
python3 -m unittest discover -s tools/tests -v
python3 tools/paper.py new my-paper --title '研究の題名' --profile empirical
```

`inbox/` は、受け取った資料を整理する前に置く場所だ。ここにある資料は、まだ根拠として確認されていない。
例えば、次のように依頼できる。

> inbox の資料から my-paper の論文を作りたい。読者は関連分野の研究者。
> 根拠が足りない主張を分け、構成を設計し、独立レビューと修正まで進めて。

> 導入を読んで何が問題なのか分からない。初読者がどこでつまずくかを調べ、
> 必要なら段落や節の順序まで直して、新しい読者で確かめて。

> この原稿を査読して。原稿は変更せず、位置・根拠・重要度・修正の条件を報告して。

[AGENTS.md](AGENTS.md) は、依頼の内容に応じて [paper-writing](.agents/skills/paper-writing/SKILL.md) などの手順を案内する。
各手順は、作業上の判断基準をまとめた [rules](rules/INDEX.md) を参照する。
対応するAI環境なら通常の文章で依頼できる。対応しない環境では `AGENTS.md` を入口として指定する。
フォルダを配置しただけで、すべてのAI環境に同じ機能が追加されるわけではない。

## 同梱する skills

| skill | 役割 |
| --- | --- |
| [paper-writing](.agents/skills/paper-writing/SKILL.md) | 分野に合わせた論文執筆、レビュー、修正 |
| [blind-referee](.agents/skills/blind-referee/SKILL.md) | `$blind-referee output/example/paper.pdf` など、明示指定の報告専用初見査読 |
| [undergraduate-lecture](.agents/skills/undergraduate-lecture/SKILL.md) | 学部水準の理解用ノート。前提知識の橋渡しと専用読者による確認 |
| [application-interview](.agents/skills/application-interview/SKILL.md) | 同じ会話での履歴書・申請書作成、途中保存、再開 |

通常の執筆、講義ノート、申請書は自然な依頼から始められる。`blind-referee` は、
原稿を変更せず、初読者の指摘だけを返すコマンドだ。使うときは明示的に指定する。
通常の執筆で初読確認が必要な場合は、執筆手順の一部として実施する。

作る成果物も通常の依頼で選べる。数学・理論研究なら、例えば次のように指定する。

> 証明集（pf）と英語論文（en）だけを作って。日本語訳と講義ノートは不要。

`pf/en`、`pf/en/ja`、`pf/en/lec`、`pf/en/ja/lec` などを選び、
選択を `design.md` に保存する。講義ノートは英語論文から直接作れる。
論文だけの構成や別言語の正本も選べる。指定のない翻訳・ノートは自動追加しない。
選択の詳しい扱いは [成果物の契約](rules/pipeline.md) を参照する。

## フォルダ

```text
AGENTS.md                  AIの入口と共通の制約
.agents/skills/            執筆・初見査読・講義・対話型申請書
.codex/agents/             Luna / Sol の実際のサブエージェント定義
.codex/config.toml         サブエージェントの同時実行数
rules/                    基本論理、文章作法、分野別検証、修正ループ
inbox/                    未整理・未検証の資料
writing/<slug>/            原稿の正本、根拠、設計、主張の記録
output/<slug>/             PDF / HTML、生成記録
refs/                     ローカルな参考文献
index.md                  全体の入口
writing/index.md          ローカル研究一覧（自動生成）
templates/                新規研究・報告書のひな型
tools/                    管理、凍結、検査と回帰テスト
evals/                    文章と運用の評価用素材
docs/                     設定、品質の範囲、保守
.paper-local/             非公開の凍結版・レビュー・読者ループ
.application-local/       非公開の申請書下書き・聞き取り状態
```

`<slug>` は `new` コマンドで指定する研究フォルダ名である。例えば `my-paper` を指定すると、原稿と記録は `writing/my-paper/` に置かれる。

`inbox/` は未整理の資料、`writing/<slug>/` は原稿と根拠・設計・主張の記録、
`output/<slug>/` は原稿から生成した PDF や HTML の保存先だ。
この三つに加え、文献と研究一覧は初期状態で Git の追跡対象外だ。
そのため、研究資料を公開用スターターへ混ぜずに利用できる。共同研究の履歴を管理する場合は、研究用リポジトリで追跡対象を明示する。

## 資料確認から改稿まで

研究用フォルダを作ったら、資料の中から使う情報を確認し、どの主張の根拠になるかを記録する。
根拠の確認では、出典の有無だけでなく、出典のどの箇所が主張をどこまで支えるかを調べる。
その後、読者と目的に合わせて構成を決めて執筆し、必要に応じてレビューと修正を行う。

独立レビューでは、執筆に関わっていない別の担当者が対象版を読み、主張・根拠・説明の不足を報告する。
執筆者は報告を原稿と根拠に照らして採否を決め、採用した指摘をまとめて修正する。
修正後は、変更箇所だけでなく、それに依存する主張や図表も確認する。
初読者には設計や期待する答えを知らせず、実際に読み進めた時点の理解を記録する。
分かりにくさが残る場合は、言い換えだけでなく説明の順序や構成も見直す。

確認範囲は変更の内容に応じて決める。誤字など意味を変えない修正は差分確認で足りることがあるが、
新しい主張や投稿前の原稿では、内容に応じて広く確認する。修正回数を先に決めて打ち切るのではなく、
採用した指摘を直し、その影響箇所を再確認して作業を終える。
[読者ループのコマンド](tools/blind-review/READER_LOOP.md) は、読者目標、対象版、観測、修正の対応を記録・検査する。
このコマンドは記録を検査するもので、執筆やAIモデルの呼び出しは行わない。
資源・権限・資料が不足する場合や、読者への情報隔離に失敗した場合は、確認を未完了として記録する。
申請書の聞き取りは本人の回答を得て進める。[保存状態](tools/application-interview/README.md)から再開できる。

[品質契約](rules/quality-contract.md)には、読者が既に知っている内容、外部資料の説明方法、引用の示し方を研究ごとに記録する。
新しい原稿では、同じ研究課題・資料・方法を扱う既刊論文を比較対象として選び、構成や説明量を検討する。
比較対象から文体を写すのではなく、原稿の構成を決める参考にする。
レビューで指摘がなかった場合も、何を確認したかを記録する。
テキストの初読には、[順次読者CLI](docs/reader-runner.md)を使って読み手の観測を保存できる。

## AI役の分担

対応するAI環境では、資料の一覧や初読時の観測と、設計・執筆・論証の判断を別の役割に分けている。
役割名やモデル設定、環境ごとの違いは[エージェント設定](docs/agents.md)を参照する。

## 出力と検証

Markdown から HTML を作る場合は Pandoc、TeX から PDF を作る場合は LuaLaTeX と latexmk が必要である。
原稿の編集、索引、レビュー記録の機能は、これらの組版ソフトなしでも使える。

```bash
python3 tools/paper.py build my-paper
python3 tools/paper.py index --check
```

TeX 原稿を作る場合は `new ... --format tex --language en` を指定する。
同梱の TeX は英語用の最小ひな型である。日本語組版や投稿先固有のクラスは、実際の環境と投稿規定に合わせて設定する。
ビルドが成功しても、出力の目視確認、提出対象だけを使った再ビルド、著者による最終通読が必要である。

レビュー対象の版を固定する方法、実際の報告を記録する方法、報告と原稿の版が一致するかを調べる方法は
[コマンド説明](tools/README.md)を参照する。
`readiness` は確認記録の不足や古さを見つける補助コマンドであり、論文の正しさを認証しない。

[品質の対応と検証状況](docs/quality.md)では、機械検査、実行したAI評価、人間による確認を区別している。
このスターターは全分野の論文を一定品質に自動で仕上げるものではない。必要な確認を定め、
どの確認を実施したか記録するために使う。

## 公開・改変

使っていて問題が起きたら、Issue での報告や修正のプルリクエストは大歓迎。
改善の提案も歓迎する。問題の報告には、再現手順や期待した動作、実際の動作を添えてもらえると助かる。

スターターのコード・自作の規則・ひな型は [MIT License](LICENSE)。
利用者が追加した原稿、データ、外部文献の権利はそれぞれに従う。
公開前に `git status --short --untracked-files=all` と実際の対象差分を確認する。
このスターターは自動でコミット、push、投稿、送信を行わない。
