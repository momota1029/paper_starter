# 指示の合議・タスク分解・証明の引継ぎ

この規則は主担当の運用を定める。モデル・推論強度と実際の起動指定は
[エージェント設定](../docs/agents.md) を参照する。主担当はユーザーが選んだ
モデルのままとし、ここで追加する解釈・分解・証明の子担当は読み取り専用の葉として報告を返す。
指示解釈や証明の役割を設計・執筆・独立レビューと混同しない。
論文制作の開始条件、分野の契約、選択した成果物、既存の権限を引き継ぐ。

## 1. Luna は作業指示ごとに Sol と意図を照合する

主担当が Luna のとき、新しいユーザーの作業指示を受けたら、依存する編集や
担当への実行依頼に進む前に `intent_interpreter` を一度呼ぶ。
曖昧な指示だけに限定しない。短い指示は短い合議でよい。
命令形に限らず、依頼や疑問の形で作業を求める発話も含む。
必要なファイルの所在や現行版など、解釈に依存しない読み取りは先に進められる。

| 入力 | 扱い |
| --- | --- |
| 作成・修正・調査・検証・証明などの新しい作業指示 | Sol と照合してから依存する作業へ進む |
| 誤字一件、索引更新、既存計画を「続けて」などの狭い指示 | 短く照合する。全体設計や全役レビューは起動しない |
| 途中の訂正、方針変更、対象や成果物の追加・縮小 | 影響する旧割当を止め、訂正と維持する制約を再照合する |
| 「止めて」「送らないで」などの停止・権限の撤回 | 直ちに従う。合議の完了を待って継続しない。新しい作業指示があれば改めて照合する |
| 挨拶、感想、進捗だけの質問、作業指示を含まない通常の説明質問 | 必須の合議は起動しない。実質的な解釈の不確かさがある場合だけ使う |
| 内部の担当依頼、担当の結果、読者の観測 | この受付を再帰的に起動しない |

主担当が Sol / Astra の場合にも、実質的な曖昧さがあれば同じ解釈役を使える。
明示的な単独作業の指定はこの既定に優先する。Luna を別の主担当へ自動変更しない。
盲検の初読者へこの規則、解釈報告、著者意図を渡さない。

### 合議に渡すものと返すもの

主担当は、ユーザーの指示原文、関係する過去の訂正・確定事項、現行の目的、
対象の版・ファイル、許可された範囲、解釈に必要な根拠の場所を渡す。
Luna の候補解釈を添えてもよいが、それだけで原文を置き換えない。
関係のない会話や私的資料を広く集めない。

Sol は次の短い報告を返す。明示された内容と推定を区別し、根拠を添える。

- 求められた結果、対象・成果物の範囲、保持する条件と禁止された変更。
- 何が揃えば今回の依頼を終えられるか、取り違えやすい点。
- 根拠から解決できる通常の判断と、どうしても不足する実質的な選択。

Luna はこの報告を指示原文・既存決定と突き合わせ、一つの実行方針にまとめて
既存の権限内で進める。合議はユーザーの明示指示を多数決で上書きする場ではない。
承認の捏造、レビューだけの依頼からの改稿、定理や成果物の黙った弱体化をしない。
通常は一つの Sol 報告で足りる。具体的な不一致や新しい根拠がある場合だけ
追加照合し、内部報告のたびに同じ合議を繰り返さない。

不一致を既存資料から解決できるなら、その理由を残して進める。
結果・対象・権限を変える未決の選択が残る場合だけ、選択肢と影響をユーザーへ
短く返す。止まるのはその選択に依存する作業だけである。
既に決まった選択や通常の実装判断を再承認の関門にしない。
長い仕事の確定事項は既存の `design.md` や作業記録へ反映し、短い修正のために
新しい台帳を作らない。保守依頼から論文プロジェクトを生成しない。

Sol を起動できない場合は、理由と合議未実施を明示し、実行済みと扱わない。
解釈に依存しない許可済みの調査は続け、解消できない選択だけを保留する。
別モデルの使用が既に許可されている場合は、実際のモデルと代替であることを残す。

## 2. タスク分解は実行を前へ進めるために使う

`intent_interpreter` は何を求められたか、`task_decomposer` はどの依存をどの順に
解けば進むか、`designer` は原稿の読者・構成・修正範囲を扱う。
解釈が揃っただけで、分解や論文設計まで必須にはならない。

複数の依存が絡む、現在の難所が曖昧、反例や方針変更で最短の経路が変わった場合に
`task_decomposer` を呼ぶ。既に次の一手が明確なら直接実行する。
通常は二〜四件、少なければ一件以下で、次の実行可能な割当を返す。

- 固定する目標と前提、必要な入力と場所、既に確定した部分。
- 具体的な成果物、担当、前提となる割当、並列化できる範囲。
- 次に実行する最小の作業、成功・反証の条件、残った場合の引継ぎ先。

現在の目的と関係のない監査や新しい前提条件を増やさない。
証明義務の改名・再分類、定理の弱体化、同じ計画の反復を証明の進捗と数えない。
分解担当は新しい仕事や権限を作らず、主担当が採用した割当を順次実行する。

## 3. Sol で構成し、具体的な証明の難所を Astra へ渡す

新しい証明や既存の穴の修復には `prover` を使う。命題の原文、全ての量化・仮定、
採用済みの定義、対象版と依存する補題を固定する。数学的な証明を必要としない
実証・解釈の仕事へ、この経路を形式だけで適用しない。

Sol が難所を残したら、主担当は次の条件を使って `prover_astra` へ引き継ぐ。
Sol 本人が子を起動する必要はない。葉からの引継ぎ報告を主担当が実際に配送する。

| 条件 | 次の行動 |
| --- | --- |
| 中核の推論に具体的な穴があり、通常の補題適用では埋まらない | その一点と成功条件をまとめ、Astra で構成・反証を試す |
| 異なる二つの方法でも同じ障害が残る | 同じ Sol 作業を再起動せず、障害を局所化して Astra へ渡す |
| 証明候補と反例候補、または独立検証の指摘が衝突する | 最初に両立しない推論と仮定を示して Astra に解決を割り当てる |
| 主担当が既知の難所を特定している、またはユーザーが Astra を指定した | 最初から `prover_astra` を選んでよい |
| 出典・入力・著者の実質的な判断が不足している | 不足を取得・照会する。モデルを替えたことを不足の解消と扱わない |

「二つの方法」はエスカレーションを促す条件で、先に失敗しなければならない
ノルマでも、研究全体を打ち切る回数上限でもない。最初の試行で難所が明確なら
直ちに引き継いでよい。通常の Sol / Astra 間の割当変更に追加の利用者承認を作らず、
明示された資源上限・モデル制約を守る。外部サービスへの送信権限は別に扱う。

### 証明の引継ぎ票

新しい履歴の担当でも推論を再開できるよう、以下を一つの短い依頼にまとめる。
必要な数式・反例は省略せず、資料の所在だけを渡して問題を丸ごと再発見させない。

| 項目 | 内容 |
| --- | --- |
| 目標 | 元の命題、量化、仮定、結論、著者が維持すると決めた定義と方針 |
| 基準版 | 対象ファイル・ラベル・版またはハッシュ、関連する証拠の位置 |
| 確定部分 | 利用できる補題と実際の導出、各補題の適用条件、未検証の依存 |
| 失敗した方法 | 試した方法と最初に成立しない推論。単なる時間切れと論理的失敗を区別 |
| 今回の一点 | 最小の未解決補題、構成、または反例の問い。全体の目標との接続 |
| 返す結果 | 完全な導出・条件付き結果・反例・残る穴のいずれかと、採否を判定する条件 |
| 実行範囲 | 読める資料、読み取り専用の報告先、実際の資源制約、他の担当との依存 |

新しい定義が必要なら対象・意味・既存の定義との関係を明示する。
目標を満たす性質を定義に埋め込む循環、仮定の密かな追加、全称命題の有限例への
置換をしない。仮定を増やした結果は条件付きとして元の命題と分ける。
計算や有限実験は、実際に試した範囲の証拠として報告する。

証明担当は、元の目標への完全な検査可能な導出、追加条件を明示した結果、
全仮定を満たして結論を破る反例、または残る推論の正確な位置を返す。
反例があるなら無理に成功へ変換せず、元の命題が偽である根拠を残す。
解けていなければ、同じ依頼を Sol と Astra の間で往復させない。
新しい補題・資料・反例検査など、障害を変える次の一手があるときだけ続ける。
必要な入力や資源がない場合は、既存の停止状態で未解決点と再開条件を残す。

### 統合と独立確認

主担当が引継ぎ報告と証明候補を既存の `evidence.md` 等へ保存し、採用した構成を
`writer` が割り当てられた証明集・原稿へ反映する。証明担当には原稿の同時編集や
台帳更新の権限を与えない。報告があるだけで `claims.json` を検証済みにしない。

確定した版に対し、証明の作成・修復へ参加していない新しい
`correctness_reviewer` 等を使い、仮定、各推論、結論、依存の接続を確認する。
Sol / Astra の合意やモデル名は数学的根拠でも独立確認でもない。
必要な専門性を確保できない場合や独立確認を実施できない場合は、
[レビュー規則](review-loop.md) に従って未確認を残す。

## 4. 同時実行と情報境界

全ての役は、主担当を除く同時三スレッドの既存上限を共有する。
合議が済んだらその報告を回収して枠を空け、必要な実行役へ渡す。
証明の通常の並列枠は二つまで、そのうち Astra は一つまでとする。
例えば独立した補題、構成と反例探索など、別々に判定できる問いを分担する。
同じ問いへの無目的な多重起動や、依存する証明とその統合を並列にしない。

子担当はさらに起動せず、主担当が残枠・依存・版を管理する。
合議・分解・証明は作成側の作業で、独立レビュー人数や `paper.py` のレビュー
報告区分に加えない。並列の結果は元の命題へ接続できるかを主担当が確認する。
途中の訂正で影響した結果だけを無効化し、無関係な完了作業までやり直さない。

## 5. 運用を確かめる例

| 依頼・状況 | 期待する動作 | 避ける動作 |
| --- | --- | --- |
| 「pf/en だけ作って」 | 指示原文を Sol と照合し、二成果物と既存の正確性条件を維持 | ja・lec を必須化、毎回再確認 |
| 「この一文字を直して」 | 短い合議後に局所修正と差分確認 | 合議の省略、分解や全体査読の必須化 |
| 「調べるだけ。原稿は直さないで」 | 読み取り専用の調査と報告 | Sol の提案を理由に原稿を編集 |
| 「今どう？」だけ | 現在の証拠から進捗を答える | 指示合議から全計画を再起動 |
| 証明に同じ量化の穴が残る | 元の量化と失敗した推論を Astra へ引き継ぐ | 仮定を追加して元の定理を証明済みにする |
| Astra が証明候補を返す | 原稿へ統合し、別の新しい担当で正確性を確認 | 証明の作成者を独立査読者として数える |

静的検査に加え、実際の起動引数、観測できたモデル・推論強度、合議の報告、
引継ぎ先を区別して点検する。詳細は [実行の確認](../docs/agents.md#読み込みモデル指定実行の確認)
に従う。設定ファイルや依頼例の存在だけで、合議やエスカレーションが実行されたとは
報告しない。この規則は主担当の判断手順であり、外部フックによる強制実行ではない。
