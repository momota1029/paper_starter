# レビュー担当と情報境界

ここでは役割の責務と情報境界を定める。実際に同梱した Luna / Sol の設定名と起動の対応は [カスタムエージェント](../docs/agents.md) に従う。人間も各レビューを担当できる。選択・人数・反復・停止は [review-loop.md](review-loop.md) に従う。異なる役割名を付けても、同一の履歴を共有した自己点検が独立レビューになるわけではない。

## 作成と判定の責務

| 担当 | 仕事 | 入力と境界 |
| --- | --- | --- |
| 統合担当 | 版とリスクを決め、指摘を実物と照合し、判断・修正・再確認を記録する | 全記録を扱える。自分の統合読みを独立判定と数えない |
| 設計担当（Spec） | 読者、主張の焦点、依存順序、残す内容、読者目標、修正範囲を定める | 原稿、根拠、著者意図、過去の採用指摘。自分の設計を独立 Audit しない |
| 執筆担当（Generate） | 確定した設計と採用指摘を一括して実装する | 設計、正本、必要な根拠。未解決の主張・範囲を独断で確定しない |
| 構造監査担当（Audit） | 設計と実際の原稿を独立に比較する | 凍結した対象版、設計、必要な根拠。設計・執筆に参加した担当は不可 |

レビュー担当は原稿を直接修正せず、観測と根拠を報告する。他の担当の未確定報告を見ずに読み終え、報告を保存してから統合する。専門担当の再確認には採用指摘と差分を渡せるが、初読担当には渡さない。

## リスクごとのレビュー

| 役割 | 起動するリスク | 確認すること | 代わりにならない確認 |
| --- | --- | --- | --- |
| 分野正確性 | 新しい／変更した結論、証明、分析、実験、専門的解釈 | 前提、手法、反例・境界、再現に必要な条件、データと結論の対応、不確かさ。適用できない項目は理由を記録 | 読みやすさ、書誌の整合性 |
| 基本論理・説明の接続 | 定義、前提、推論、専門的入力の適用、翻訳・圧縮 | 語や対象の意味、必要な命題の明示、前提から結論への飛躍、循環、条件の脱落、引用した手法の適用条件と今回の対象の対応 | 分野専門家による正確性の検証 |
| 根拠・引用支持 | 主張、帰属、新規性、既知の結果、引用位置の変更 | 実際の一次資料を読み、正確な該当箇所が対象主張をどの範囲で支持するか。矛盾する資料、版の違い、未入手を記録 | 参考文献一覧やリンクが存在するだけの確認 |
| 書誌・引用関係 | 引用キー、文献情報、資料の同一性、配布・投稿物の変更 | 本文の引用 → 書誌項目 → 実際の資料 → 配布物の関係、欠落、重複、誤同定、利用できない内部依存 | 引用元が本文の主張を本当に支持するかの確認 |
| 構造 | 節順、情報配置、重点、統合・分割、圧縮 | 節ごとの役割、先行依存、重複、必要な中核の保持、全体の主張と説明量の対応 | 独立の初読、内容の正確性 |
| 導入 | 導入の新規執筆・再構成、関連研究・背景・主張の予告 | 問題設定、主張と範囲、先行研究との関係、本文との一致、宣伝的な強調、予告の回収 | 原稿全体の構造監査、初読 |
| 分野・媒体慣行 | 近接例や投稿先の形式に依存する構成判断 | 実際に読んだ近接資料に基づく構成、根拠提示、説明量。媒体の要件と単なる慣習を区別 | 一般的テンプレートへの一致だけの判定 |
| 規則・表現 | 表記、用語、参照、媒体要件、プロジェクトの明示規則 | 適用する規則と位置を対応づける。定義・記号・略語の初出、意味の一貫性、図表と本文・参照の整合 | 内容の正確性、人間の理解 |
| 比較文章評価 | 意味・範囲を維持した文章改善で固定した改稿前版がある | 最初の比較基準に対する明確さ・流れ・簡潔さの改善。単なる言い換え、不要な増量、情報欠落 | 初読の観測、主張が異なる版の優劣判定 |
| 初読者 | 読者理解が目的、読者向けの新規原稿・大幅改稿 | 実際に前から読んだ時点の理解、混乱、誤解、未回収の予告と本文の根拠 | 正確性の証明、設計の自己認証、人間の最終通読 |

基本論理の担当は、想定読者が持つ一般的知識を前提にしてよいが、未導入の専門事項を善意で補完しない。分野正確性の担当と必要な専門性が違う場合は別に置く。限られた人数で一人が複数リスクを確認する場合も、各領域の観測・未確認事項を分けて報告する。初読と設計、初読と修正、設計と独立 Audit は兼務しない。

## 初読者への渡し方

渡してよいものは、中立な一文の読者属性と、凍結原稿の読み進めた範囲だけである。例: 「関連領域の基礎を学んだ読者として、この解説を読む」。本文から何を答えてほしいかを読者属性に混ぜない。

次は渡さない。

- `design.md`、読者目標、期待回答、採否基準。
- 改稿差分、修正指示、過去の会話や評価、執筆者の成功報告。
- 別の読者・専門担当の報告、未読の後続部分。

同じ会話を新しい役割名で続けることは初読の独立性を満たさない。利用する仕組みが親の履歴を引き継ぐなら、履歴のないセッションか、事前情報を持たない別の人間に切り替える。隔離を保証できなければその事実を記録し、初読済みとは報告しない。

読み方は [前方読みの手順](review-loop.md#実際に前から読む) に従う。次のまとまりを開く前に観測を保存する。観測を提出してから設計側が目標と照合する。本文から分からない箇所は分からないまま報告し、読み手に代案の執筆や著者意図の推定を求めない。

## 報告と未実施の扱い

各担当は対象版、役割、実行日時、入力資料、読んだ範囲、未読・未入手の範囲、指摘の正確な位置、根拠、重大度を残す。「問題なし」の場合も、何をどこまで確認したかを明記する。初読ではさらに各チェックポイントの順序、提示範囲、観測と回復位置を記録する。

初読者以外の専門担当にも、執筆者の結論を追認するような指示を与えない。実物・一次資料・計算・具体例等から判定し、確認できない点を分離する。複数 AI の一致は人間による承認や事実の証明ではない。

単独作業時はこれらを自己点検の観点として使い、担当を演じ分けた数を独立レビュー人数として数えない。未実施の独立確認と人間の最終通読を明示して引き継ぐ。ローカルツールの出力、記録形式、操作は [tools/README.md](../tools/README.md) を参照する。どのツールも、報告の雛形を生成しただけでレビューを代行したことにはならない。
