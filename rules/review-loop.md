# レビュー・修正・再確認

この手順は論文、報告書、解説、翻訳などに共通する。分野・媒体に固有の正しさは、対象の設計と根拠資料で定める。役割と情報境界は [reviewer-roles.md](reviewer-roles.md)、補助 CLI の操作と記録形式は [tools/README.md](../tools/README.md) を参照する。ツールを使わない場合も、以下の版固定・独立確認・判断記録を実行する。

## 1. 対象とリスクを決める

改稿対象の正本を一つに定める。開始前に対象版、変更目的、変更してよい範囲、維持する主張・引用・用語、想定読者、終了条件を記録する。既存の指摘を読み、検証済みの内容、新規の内容、未解決の内容を分ける。未解決の内容を確定した事実として圧縮・採用しない。

最も軽い十分なモードを選び、実際に変わるリスクから担当を選ぶ。人数は**一ラウンドの上限**であり、総ラウンド数の打ち切り条件ではない。設計者と執筆者は作業量に含めるが、独立レビュー人数には含めない。

| モード | 変更と目的 | 一ラウンドのレビュー予算 | 通常の開始計画 |
| --- | --- | --- | --- |
| L0 | 意味を変えない誤字、リンク、メタデータ、機械的整理 | 0 人。意味や参照への影響が疑わしい場合のみ 1 人 | 静的確認と差分確認で閉じる |
| L1 | 一節内の説明改善、既存内容の明確化、局所的引用修正 | 1 人、異なるリスクがある場合は 2 人まで | 診断・修正・該当箇所の再確認 |
| L2 | 新規原稿、大幅改稿、主要節の追加・移動、媒体変更、新規主張・分析 | 4 人まで。独立 Audit を含む | Spec → Generate → Audit を行い、診断と修正確認の 2 ラウンドを見込む |
| L3 | 投稿・配布・公開直前、明示された全体レビュー、高リスクの中核変更 | 7 人まで。初読者は 2 人まで | 必要な全領域を確認し、未解決事項の閉鎖まで続ける |

L2 の読者理解の改稿で、分野慣行、構造 Audit、基本論理、初読、導入の 5 領域が同時に必要なら、理由と担当を先に記録して 5 人まで使える。それ以外の増枠も、異なるどのリスクに必要かを開始前に説明する。独立した範囲を次ラウンドへ分けることもできるが、必要な確認の省略を収束としない。

内容の正確性が変わる場合は分野正確性の確認、前提・定義・推論の接続が変わる場合は基本論理の確認を選ぶ。この二つを読者の「分かった」で代用しない。引用元が実際に主張を支えるかという確認と、引用キー・書誌・配布物の整合性確認も別である。役割一覧の全員を毎回起動する必要はない。

## 2. 版と証拠を固定する

レビュー開始時に原稿と必要な入力を固定する。対象ファイル、取得日時、ハッシュまたは版識別子、読む範囲、添付資料、担当の役割を残す。行番号だけでなく、節・ラベル・短い引用など再同定できる位置も記録する。

補助ツールを使う場合、`.paper-local/reviews/<slug>/<run>/` の凍結入力と manifest は対象版の証拠になる。**作成されたレビュー用資料は、レビューを実行した証拠ではない。** 実際の担当者・実行日時・読了範囲・観測・指摘を持つ報告を別に保存する。空の報告書、雛形、コマンド成功、自己申告だけから独立レビュー済みとしない。

手作業なら、別ディレクトリの読み取り用コピー、ファイル一覧と版識別子、独立した報告書で同じことを行う。初読者には必要な原稿の断片だけを順に渡し、設計や他の報告が見える共有フォルダ・会話履歴を渡さない。ファイルを凍結しただけでは情報隔離は成立しない。

実務上の判断はプロジェクトの記録へ反映する。`meta.toml` は進行状況、`evidence.md` は根拠と限界、`claims.json` は重要な主張の検証状態、`design.md` は設計・読者目標、`corpus.md` は参照した近接例を扱う。具体的な形式はツール文書に従い、存在しない検証結果を埋めない。必要なレビュー台帳は追記方式で残し、過去の報告を新しい結論で上書きしない。

## 3. 大幅変更では Spec / Generate / Audit を分ける

1. **Spec（設計）**: 読者に残す中心内容、節ごとの役割と依存、残す・圧縮する・引用する・移す・除く内容、表現形式、読者目標、変更限界を定める。分野慣行に依存する判断は実際に読んだ近接資料と位置を `corpus.md` に記録する。独特な表現を模写せず、構成・根拠提示・説明量の判断を参考にする。
2. **Generate（執筆）**: 採用された設計と、まとめた修正指示に従って執筆する。新しい主張、論拠、用語、範囲変更が必要になった場合は決定事項として戻す。すでに与えられた権限内の実装判断に改めて承認を要求しない。
3. **Audit（独立監査）**: 設計・執筆を担当していない新しい担当が、実際の改稿と設計を照合する。各主要部分の新情報、重複、削除による損失、依存順序、必要な根拠、圧縮で失われた条件を確認する。

設計者が自分の設計を監査した報告や、執筆者の自己点検を独立 Audit と数えない。分野上の結論・公開範囲など著者の判断が必要なら、選択肢と影響を具体化して記録する。訳文の改善を理由に原文の主張や構成を黙って変更しない。

## 4. 初読の期待と観測を分離する

読者理解が目的の新規執筆・大幅改稿では、設計時に次を固定する。

- 自然な読み始め、読者の既有知識、読み終える範囲。
- どの自然な区切りまでに、読者が何を本文から説明できるべきか。
- 必須目標と任意目標。先に予告し、後で定義することを許す箇所。
- 維持する主張・引用・用語と、修正の上限（文／段落／節／全体構成）。

目標は「この順で書く」という目次ではなく、観測可能な理解で書く。例えば「導入末で、問題・主張の範囲・既存研究との差を本文の位置とともに説明できる」。全原稿へ同じ新規性や難所を強要しない。既存原稿では改稿前の版も固定する。

初読者は新しい独立した読者・セッションを使い、原稿と中立な一文の読者属性だけを受け取る。設計、目標、期待回答、改稿意図、差分、過去の会話・報告、他の読者の報告を渡さない。修正後も同じ読者を使い回さない。

### 実際に前から読む

1. 読み始めから一段落、または自然なまとまりだけを渡す。後続本文を先に読み込ませない。
2. **次のまとまりを渡す前に**、ここまでの理解、現在の段落の役割、予告された見返り、次に必要だと感じた説明、最初につまずいた語句・位置、根拠となる本文、未読範囲を保存する。時刻または順序を残す。中立な質問として、対象と範囲、仮定・量化、結論、各段階を支える本文、制限も自分の言葉で説明してもらう。「主張された」と「根拠を読んだ」を区別する。同じ質問を各区切りで使い、目標に応じた穴埋めや正解候補を示さない。未提示なら未提示と答えてよい。
3. その後で次のまとまりを渡す。後で混乱が解けたら回復位置を追記し、最初の混乱を消さない。
4. 自然な区切りごとに、本文から復元できた内容を短く報告する。本文にない内容は `unsupported` とする。内部思考の逐語記録は求めない。

全文を先にコンテキストへ載せた後で「最初はこう感じた」と再構成しても、この確認にはならない。閲覧ツールが全文を載せる場合は `ISOLATION_FAILED` を記録し、前方読みを未実施として残す。手作業で一片ずつ渡す方法へ切り替えられる。

### 観測を照合する

全員が報告を保存した後で、設計担当と統合担当が目標に観測を対応づけ、`recovered / partial / missing / misread` を根拠付きで記録する。後の節で理解できても、前の区切りの必須目標を達成したことにはならない。読者間の違いを多数決で消さない。

`partial` のうち、回答に必要情報がなく理解を判定できない場合は **観測不足** と
明記する。本文にない／読み違えた場合と区別する。「概ね分かった」という申告や
条件の単語の出現だけで合格にしない。報告の前後で説明が矛盾する場合も、正しい
側だけを選んで理解済みにしない。観測質問を改善する場合は手法変更として残し、
旧結果は保持して、新しい素材で再確認する。

native の新規セッションでもプロジェクト指示が自動注入される場合がある。
fresh context と情報隔離は別である。補助の
[順次読者CLI](../docs/reader-runner.md)を使うときは輸送方法を区別して記録し、
診断の限界・実行ログ・本文提示順・目標照合を確認する。自己申告の整合だけで
隔離成立を確定しない。

つまずき、戻り読み、目的の見失い、誤解、予告の未回収は内容の重大度と別に扱う。`minor`、一文では直せない、現在の修正範囲外という理由で必須目標を閉じない。範囲外なら設計へ戻す。誤検出を退ける場合は、実際の本文、想定知識、契約上許した後の説明を特定する。

初読者は代案や書き換え文を作らない。期待と観測を照合した後に、設計担当が最小限で一貫した修正を定める。目的が不明な内容を移す・圧縮する必要がある場合、末尾への説明追加だけで済ませない。読みやすさのために主張を強めたり弱めたりしない。

## 5. 指摘を判定し、一括で修正する

各指摘に識別子、対象版、担当、正確な位置・引用、根拠、重大度、期待した状態と実際の状態を付ける。

- `BLOCKING`: 中核の成立、必要な根拠、公開条件を確認できず、そのまま進められない。
- `major`: 結論・解釈・構造・必須の理解に実質的な影響がある。
- `minor`: 局所的な改善。重大度とは別に必須目標への影響を記録する。

報告は候補であり判決ではない。統合担当は現行正本と根拠に照らし、採用・不採用・対象外を理由付きで記録する。外部報告の対象版が不明なら、その不確かさも残す。競合する提案は執筆前に解消し、採用した指摘を一つの修正束にまとめる。指摘一件ごとに執筆・ビルドを繰り返さない。

修正後に必要なビルド・静的確認・本文の統合読みを実行し、次の独立確認へ送る。状態は少なくとも「未解決」「修正済み・再確認待ち」「再確認して閉鎖」「不採用／対象外」を区別する。修正しただけでは閉鎖しない。軽微な変更のみで意味・依存・構造が変わらない場合は、統合担当の差分確認で閉じられる。理由を残す。

## 6. 再確認は依存範囲を追う

修正後の新しい専門担当には、採用指摘、変更箇所、直接依存する定義・主張・根拠・参照・節を渡す。初読者にはこれらを渡さず、修正版を自然な入口から対象区切りまで改めて読ませる。各担当は確認した範囲と未読範囲を明記する。

変更の依存先がない既確認部分は引き継げる。要旨、導入、節順、全体の用語、中核主張、他成果物との契約が変わる場合は、関連する全体へ確認を広げる。節削除や構成変更では、削除した定義・前提の残存利用、参照、図表、引用、過去の指摘（以前の対象外も含む）を再評価する。翻訳や要約で上流の欠陥を発見したら、正本を直し、影響する派生成果物へ伝播させる。

引用修正では、主張から一次資料の該当箇所への支持関係と、引用キーから書誌・資料同一性・配布物への関係をそれぞれ再確認する。文章改善の比較担当は、直前版だけでなく最初に固定した比較基準も使い、不要な長文化や言い換えの累積を検出する。

## 7. 収束・差し戻し・停止を明示する

改稿権限のある依頼では、採用した修正 → 影響範囲の検査 → 新しい独立確認を、
以下の収束条件を満たすまで繰り返す。通常の二回・三回を打ち切り理由にしない。
native初読のPDF／Markdown／テキストでは [reader-loop の状態管理](../tools/blind-review/READER_LOOP.md) で、
変更できない目標、最初の比較基準、入力の版、実際の観測、採用した修正、次の版を
接続する。コマンドは記録と遷移を検査するだけであり、実際の執筆・読者起動は
主担当が行う。`max_rounds` の既定は無制限、明示した資源上限だけが打ち切りになる。
別形式・手作業・補助読者CLIでも同じ契約と反復を既存台帳へ記録する。
補助CLI固有のreceiptをnative用の観測形式へ無理に埋め合わせない。
単独の初見査読・診断は報告のみで、ループを理由に改稿へ移行しない。
履歴書・申請書の聞き取りは別の skill に従い、本人の回答待ちで停止する。

通常の収束には、採用済み `BLOCKING / major` が閉鎖され、修正依存範囲の再確認が終わっていることが必要である。読者理解のタスクでは、さらに必須目標が実際の観測から復元され、採用した読書障害が残っていないことを要する。静的検査の成功、指摘件数ゼロ、複数 AI の賛成だけでは代用できない。

後続ラウンドでより重大な問題が生じた場合、または同じ障害が残り続ける場合は、直近の修正・依存・設計へ戻る。各追加ラウンドは採用した修正を試すか、新しい根拠を得る明確な目的を持つ。変更も新情報もない再実行、合格するまでの読者の引き直し、合格させるための目標の弱体化をしない。目標自体が誤っていたなら、根拠と変更理由を残して新しい設計にする。

| 停止状態 | 意味と引継ぎ |
| --- | --- |
| `CONVERGED` | 宣言した範囲の指摘と必須目標を閉鎖。範囲外の品質保証ではない |
| `RETURN_TO_DESIGN` | 修正範囲不足、矛盾、発散。失敗箇所と必要な設計判断を残す |
| `AUTHOR_DECISION_REQUIRED` | 結論・範囲等の著者判断が必要。選択肢と影響を示す |
| `EXTERNAL_BLOCKED` | 一次資料や必要な環境などが不足。未確認事項と再開条件を示す |
| `BUDGET_EXHAUSTED` | 合意した実行資源が尽きた。未解決事項を残し、合格にしない |
| `ISOLATION_FAILED` | 期待回答の漏洩や先読み等。該当する独立性・初読確認を無効とする |
| `INDEPENDENT_CHECKS_INCOMPLETE` | 独立担当が不在・未実施。自己点検と未実施領域を分ける |
| `HUMAN_READ_PENDING` | 最終版の人間による通読が未完了。公開前の完了扱いにしない |

未実施の確認、隔離失敗、外部待ち、予算切れはそれぞれ記録する。複数が該当するときは一つの状態に隠さない。総ラウンド数の固定上限は設けず、進展のない無限反復も行わない。

## 8. 人間の最終通読と引継ぎ

公開・配布の前に、人間が現行版を最初から最後まで読み、実際の表示・組版も確認する。理解したという著者の自己評価を AI が代記して確定しない。全指摘の最終棚卸し、必要な内容・引用支持・書誌関係の確認、対象版の一致を確かめる。最終確認後に内容が変われば、その依存範囲の確認を更新する。

最終報告には対象版、実施した確認と証拠、未実施範囲、残る判断、人間の通読状況を短く示す。`CONVERGED` は指定したレビュー範囲の終了であり、人間の可読性、分野的正しさ、投稿適格性の万能な認証ではない。CLI の readiness 等も、入力と記録を点検する補助であり、本文を読んだ人間や独立レビューを生成しない。

単独作業の指定や独立担当を用意できない場合でも、許可された執筆・根拠確認・ビルドは進められる。同じ担当が設計、執筆、自己点検を時間的に分け、その事実、独立レビュー人数 0、未確認項目を明記する。名称を変えた役割や新しいプロンプトだけで独立性を主張せず、`INDEPENDENT_CHECKS_INCOMPLETE` を残す。
